# Planning (grill-me)

Когда читать: триггер `grill me` / `grill` / «погриль» / «составь план» / «план» (старт опроса), или Plan mode (`EnterPlanMode`) до согласования.

Вне planning — не засыпать вопросами.

Платформа, стек, слои, DI — [architecture.md](architecture.md) / [../../CLAUDE.md](../../CLAUDE.md) §2. Стиль — [codestyle.md](codestyle.md). Исключения — [exceptions.md](exceptions.md). Принципы craft — [../../CLAUDE.md](../../CLAUDE.md) §3. Unity/Rider tooling — [unity-mcp.md](unity-mcp.md) / [rider-mcp.md](rider-mcp.md). В planning **не дублировать**.

## Pre-flight (до первого decision-вопроса)

Зафиксировать или уточнить 2–4 вводных **одной** пачкой (`AskUserQuestion`):

- масштаб / числа, если важны для задачи
- прежние попытки — что пробовали и почему отвергли
- constraints — что нельзя менять (API, prefab, сцена)
- остальное из контекста и [architecture.md](architecture.md) — зафиксировать явно, не переспрашивать

Новая вводная **mid-grill** → остановить, перепланировать дерево.

## AskUserQuestion

- Decision-вопросы — через `AskUserQuestion` (предпочтительно)
- Tool недоступен → **явно сказать**; предложить ответить текстом (номер / label варианта)
- Pre-flight — одна пачка; дальше **один** decision-вопрос за раз

## Grill rules

1. Один decision-вопрос за раз
2. 2–4 варианта; рекомендуемый — первый, «(Рекомендуется)» в label
3. Адаптировать дерево — не задавать потерявшие смысл вопросы
4. Ответ в коде — читай репозиторий, не спрашивай
5. Краткий контекст (1–2 строки); без «сейчас Q3» и прочих процессных реплик
6. **Не поддакивать** — противоречия с кодом, `.claude/rules/`, планом — с цитатой
7. Сверка: новый ответ не ломает уже зафиксированное
8. Сомневаешься — codebase / Context7 / docs / search; не угадывай

## Закрыть до плана

- Scope (входит / не входит)
- API shape (имена, типы, конфигурация)
- Lifecycle (создание, уничтожение, фазы)
- Edge cases (прерывания, повторный ввод, busy)
- Смежные механики (из architecture / соседних фич)
- Файлы и слои, порядок изменений
- Риски и проверка (gameplay-сцена / TEST — по проекту)

## Пайплайн: вопросы → готовность → footer

```
вопросы (по одному)
        │
        ▼
агент уверен: открытых веток нет
   (или юзер: «всё» / «хватит» / «составляй план»)
        │
        ▼
показать footer (AskUserQuestion / fallback)
        │
        ▼
действие только по выбору / кодовой фразе
```

- Пока есть сомнения — **только вопросы**, footer не показывать.
- **Не** вызывать план / implement / copy / save автоматически после готовности.

## Footer после готовности

Один footer на оба этапа (grill закрыт и план уже есть). Markdown-список **не** кликабелен — footer = **`AskUserQuestion`** с опциями ниже.

Опции (порядок фиксирован):

1. «го» / `implement` — выполнение (код) — **только если** план уже зафиксирован (`ExitPlanMode`); иначе сначала создать план
2. `create plan` / «покажи план» / «составляй план» — зафиксировать или снова показать план (`EnterPlanMode` → `ExitPlanMode`)
3. `grill me` — ещё вопросы
4. `copy prompt` — копируемый `[TODO]`-блок
5. `save prompt` — `Prompts/<feature>.md` вне `Assets/`

Tool недоступен → явно сказать; тот же список текстом; предложить ответ номером / фразой.

Перед кодом — **ждать** выбор 1 / «го» / implement / явный ok **после** согласования плана.

## Кодовые фразы: copy / save prompt

| Действие | Фразы (равнозначны) |
|---|---|
| Копируемый блок | `copy prompt`, «скопируй промпт», «копируемый промпт» |
| Файл `Prompts/` | `save prompt`, `save prompts`, «сохрани промпт», «сохрани в prompts» |

**Не** триггерят prompt: «сохрани план», `create plan`, «составляй план».

### Формат промпта (`copy prompt` / `save prompt`)

- Блок контекста: `@` только нужные файлы
- Каждый шаг-изменение — `[TODO]`
- Точные сигнатуры (имя, параметры, возвращаемый тип), имена классов и файлов
- Стиль: сухой, технический; без мотивации, преамбул и альтернатив
- В конце: `Проверка: …`
- `copy prompt` — отдельный копируемый код-блок в чате
- `save prompt` — тот же контент в `Prompts/<feature-kebab-case>.md` (**вне** `Assets/` — Unity не импортирует); при правках плана — обновлять файл

Шаблон:

```
Контекст: @Path/To/FileA.cs @Path/To/FileB.cs

[TODO] 1. FileA.cs: добавить метод `ReturnType MethodName(ArgType arg)` — <что делает>
[TODO] 2. FileB.cs: изменить `ExistingMethod` — <точное изменение>
...
Проверка: <как убедиться, что работает>
```

## Не делать

- Меню без рекомендации
- Несколько decision-вопросов сразу
- Комментарии о процессе («сейчас Q3»)
- Игнорировать контр-аргументы пользователя
- План / copy / save / implement без соответствующей кодовой фразы или выбора footer
- Дублировать architecture/стек/платформу в этом файле
- Показывать footer, пока есть открытые ветки / сомнения
