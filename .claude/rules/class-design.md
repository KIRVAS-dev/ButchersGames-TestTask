# Class design

Когда читать: `ButchersGames/Assets/_Project/Scripts/**/*.cs`.

Качество типа как абстракции. Слои — [architecture.md](architecture.md); SOLID — [../../CLAUDE.md](../../CLAUDE.md) §3; методы — [method-design.md](method-design.md); формат — [codestyle.md](codestyle.md).

## АТД (класс = данные + операции)

Класс — абстрактный тип данных проблемной области, не «корзина» несвязанных полей/методов.

- Интерфейс описывает **что** делает сущность, не **как** устроена реализация
- Клиент не трогает внутренние данные напрямую и не дублирует низкоуровневые операции снаружи
- Детали реализации меняются в одном месте; клиенты зависят только от публичного контракта

Finding: клиентский код манипулирует полями/флагами/внутренним представлением вместо методов абстракции; набор методов без единой цели.

## Интерфейс и связность

- Одна **главная цель**; имя класса её отражает
- Методы интерфейса — **согласованный уровень абстракции**
- Высокая связность: всё в типе служит одной абстракции; чужое — вынести
- Предпочитать **программный** контракт (типы, сигнатуры) семантическим правилам «сначала вызови A, иначе B упадёт»
- Новый метод: «укрепляет абстракцию или размывает?» — иначе другой тип / другой слой

Finding: god-интерфейс; разнородные сервисы в одном типе; публичный API, который нельзя использовать без знания внутренней последовательности вызовов.

## Инкапсуляция и сопряжение

- Минимальная видимость членов; **без публичных полей** состояния (исключения — явные DTO/`record`/readonly-конфиги по [architecture.md](architecture.md))
- Не светить закрытые детали в публичном API
- Слабое сопряжение: меньше прямых и цепочек вызовов в чужие типы (`a.B().C().D()`)
- Видимость по умолчанию — `internal`. `public` только если тип или член нужен другой сборке

Finding: утечка реализации; жёсткая связь через детали; клиент знает внутренности лучше, чем документированный API; `public` у типа или члена, которого нет ни в одной другой сборке.

### Видимость сборки (`internal` vs `public`)

По умолчанию `internal`. `public` — только когда другая сборка (`asmdef`) реально именует тип или член: вызов, поле, базовый тип, реализация, `new`, DI `Register<T>` / `RegisterEntryPoint<T>`.

`public` оставить, даже если реализация «внутри фичи»:

- конкретный тип, который регистрирует чужая сборка (Bootstrap → Model, Service, View, Presenter)
- порт `Api/`, который реализует или вызывает чужая сборка
- член неявной реализации public-интерфейса и `override` — доступ совпадает с контрактом
- конструктор, который вызывает чужая сборка
- public-поле `MonoBehaviour` / `ScriptableObject`: Unity сериализует public-поля и `[SerializeField]`. Сужение до `internal` или `private` без `[SerializeField]` стирает данные инспектора. Если снаружи сборки поле не читают — `[SerializeField] private`, не голый `internal`

`InternalsVisibleTo` не добавлять, чтобы выдать `internal` наружу. Другой сборке нужен тип — он `public`.

Член `internal`-типа снаружи сборки и так не виден. В новом коде у такого члена тоже `internal`, кроме реализации интерфейса и сериализуемого поля.

### Explicit vs implicit реализация интерфейса

Если член можно сделать **explicit** (`IFoo.Bar`) без накладных расходов и усложнения кода — **в приоритете explicit**: нет правок call sites (потребители уже через порт/`I*`), нет лишних cast’ов внутри класса.

**События (`event`) — исключение:** всегда **implicit** (`public event …`). Explicit для events в C# требует `add`/`remove` + backing и даёт шум без выигрыша — под правило explicit не попадают.

**`IValidatable` на owned config (SO) — исключение:** всегда **`public void Validate()`**. Владелец держит concrete `_config` и зовёт напрямую; explicit даёт только `((IValidatable)_config)`. View/MB — explicit ([exceptions.md](exceptions.md)).

Implicit (`public Bar`) также — когда explicit ломает удобство или требует переписывания: вызовы через concrete-тип, Unity/сериализация, заметно более громоздкий код ради одной формальности.

Finding: public-метод/свойство интерфейса на concrete, хотя все потребители ходят через порт и explicit был бы безболезненным; либо explicit-event с backing ради формальности.

## Наследование vs композиция

- Наследование — только отношение **«является»** + принцип подстановки (Liskov). Иначе — **композиция**
- Нужна реализация, но не интерфейс базы → композиция, не наследование
- Не переопределять то, что задумано как непереопределяемое; `sealed` / невиртуальные члены, если наследование не планируется ([codestyle.md](codestyle.md))
- Множественное наследование реализаций — только после явной оценки; предпочтительны интерфейсы + композиция

Finding: наследование «ради переиспользования кода»; deep hierarchy; ломка контракта базы в наследнике.

## Когда создавать класс / чего избегать

**Создавать**, если есть ясная причина: модель сущности/абстракции; снизить или изолировать сложность; скрыть реализацию; ограничить зону изменений; упаковать родственные операции; точка управления.

**Избегать:**

- «Божественный» класс, который через get/set управляет всеми остальными
- Класс/`record` только с данными без поведения → DTO в `Api/`; бизнес-правила — в Service, не в DTO
- Класс-глагол без состояния (`*Initializer`, process-only) → метод другого типа или static Helper
- Тип «на будущее» без второго потребителя (YAGNI — [../../CLAUDE.md](../../CLAUDE.md) §3)

Роли Model / Service / View / InputHandler — **не** отменяют эти критерии: каждый тип — связная абстракция своего слоя ([architecture.md](architecture.md)).

## WebGL-Template

- **Сборка:** `public` только у типов и членов, которые именует другая сборка. Порт `Api/` (`I*Service`, `I*View`, `I*Provider`, DTO, exception) — `internal`, пока на него нет ссылки снаружи. Конкретный Model/Service/View, который регистрирует другая сборка, остаётся `public`
- **DTO / Models:** `record` или plain class с данными — ok в `Api/`; минимальные `CopyWith*` допустимы; правила — в Service
- **Managed OOP** (Model, Service, View, Bootstrap): **class** / `record` по умолчанию; не вводить `struct` «ради perf» без нужды
- **ViewComponents / Input:** presentation и адаптеры; без бизнес-правил Core
- **Helper:** `internal static class {Feature}Helper`, если его не зовёт другая сборка; иначе `public`. Stateless pure functions ([codestyle.md](codestyle.md)); domain-math в Core, view-math во ViewComponents

## Soft-check для агента

Перед новым типом или расширением публичного API: цель → согласованный интерфейс → инкапсуляция → `internal`, если другую сборку тип не называет → композиция vs наследование → не god / не verb-only.
